Qu'est-ce que Kafka Streams ?

Kafka Streams est une librairie de traitement de flux intégrée directement à Apache Kafka. Contrairement à Flink ou Spark Streaming, elle ne nécessite aucun cluster externe — tu déploies ton app Spring Boot et c'est tout.

→

Topic / Partitions
→
Kafka Streams
Spring Boot App
→
Output Topic

Notre cas d'usage : une application de commandes e-commerce. On reçoit des événements bruts sur orders-topic, on les filtre, enrichit et agrège en temps réel, puis on publie le résultat sur orders-enriched.

Configuration application

    bootstrap-servers: localhost:9092
    streams:
      application-id: orders-streams-app
      default-key-serde: org.apache.kafka.common.serialization.Serdes$StringSerde
      default-value-serde: org.apache.kafka.common.serialization.Serdes$StringSerde

        commit.interval.ms: 1000
        cache.max.bytes.buffering: 0 # désactive le cache pour démo
application-id — Identifiant unique de ton app. Kafka l'utilise pour les consumer groups et les changelogs d'état. Change-le si tu déploies plusieurs instances différentes.

ÉTAPE 05

La topologie Kafka Streams

C'est le cœur du tutoriel. On construit un pipeline filter → map → branch → aggregate en utilisant l'API DSL de Kafka Streams.

SOURCE ← orders-topic
filter(status == CONFIRMED)
mapValues(enrich)
to → orders-enriched
groupBy(customerId)
aggregate → customer-totals (KTable)
OrderStreamTopology.javaJAVA
@Configuration
@EnableKafkaStreams
public class OrderStreamTopology {

    private static final String INPUT_TOPIC  = "orders-topic";
    private static final String OUTPUT_TOPIC = "orders-enriched";
    private static final String TOTALS_TOPIC = "customer-totals";

    @Bean
    public KStream<String, Order> ordersStream(
            StreamsBuilder builder,
            OrderSerde orderSerde) {

        // 1. Source : lire le topic d'entrée
        KStream<String, Order> stream = builder.stream(
            INPUT_TOPIC,
            Consumed.with(Serdes.String(), orderSerde)
        );

        // 2. Filter : on ne traite que les commandes confirmées
        KStream<String, Order> confirmed = stream
            .filter((key, order) ->
                "CONFIRMED".equals(order.status()));

        // 3. MapValues : enrichir (ex : ajouter un timestamp)
        KStream<String, Order> enriched = confirmed
            .mapValues(order -> new Order(
                order.id(),
                order.customerId(),
                order.product().toUpperCase(), // enrichissement
                order.amount(),
                "PROCESSED"
            ));

        // 4. Sink : écrire sur le topic de sortie
        enriched.to(OUTPUT_TOPIC,
            Produced.with(Serdes.String(), orderSerde));

        // 5. Aggregation : total des montants par client (KTable)
        enriched
            .groupBy(
                (key, order) -> order.customerId(),
                Grouped.with(Serdes.String(), orderSerde)
            )
            .aggregate(
                () -> 0.0,                           // initializer
                (custId, order, total) ->
                    total + order.amount(),          // adder
                Materialized.<String, Double>
                    as("customer-totals-store")
                    .withValueSerde(Serdes.Double())
            )
            .toStream()
            .to(TOTALS_TOPIC,
                Produced.with(Serdes.String(), Serdes.Double()));

        return confirmed;
    }
}
KTable vs KStream — Un KStream est un flux d'événements append-only. Un KTable est une vue agrégée (la dernière valeur par clé). Ici, customer-totals-store est un state store local — interrogeable via une API REST interactive.
ÉTAPE 06

Tester avec un Producer

OrderProducer.javaJAVA
@Component
public class OrderProducer {

    private final KafkaTemplate<String, Order> kafkaTemplate;

    public OrderProducer(KafkaTemplate<String, Order> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public void sendOrder(Order order) {
        kafkaTemplate.send("orders-topic", order.id(), order);
    }
}
OrderController.java — Endpoint REST pour testerJAVA
@RestController
@RequestMapping("/orders")
public class OrderController {

    private final OrderProducer producer;

    @PostMapping
    public ResponseEntity<String> createOrder(
            @RequestBody Order order) {
        producer.sendOrder(order);
        return ResponseEntity.ok("Sent: " + order.id());
    }
}

ÉTAPE 07

Interroger le State Store

Kafka Streams maintient un state store local (RocksDB) qu'on peut interroger directement depuis l'app Spring Boot — sans passer par un topic :

CustomerTotalsController.javaJAVA
@RestController
@RequestMapping("/totals")
public class CustomerTotalsController {

    private final KafkaStreamsInteractiveQueryService queryService;

    @GetMapping("/{customerId}")
    public Double getTotal(
            @PathVariable String customerId) {

        ReadOnlyKeyValueStore<String, Double> store =
            queryService.retrieveQueryableStore(
                "customer-totals-store",
                QueryableStoreTypes.keyValueStore()
            );

        Double total = store.get(customerId);
        return total != null ? total : 0.0;
    }
}

BONUS

Fenêtrage temporel (Windowing)

Tu veux le CA par client sur les 5 dernières minutes ? C'est natif dans Kafka Streams :

Windowed aggregationJAVA
enriched
    .groupBy(
        (key, order) -> order.customerId(),
        Grouped.with(Serdes.String(), orderSerde)
    )
    .windowedBy(
        TimeWindows.ofSizeWithNoGrace(
            Duration.ofMinutes(5)
        )
    )
    .aggregate(
        () -> 0.0,
        (custId, order, total) -> total + order.amount(),
        Materialized.<String, Double, WindowStore<Bytes, byte[]>>
            as("customer-5min-store")
            .withValueSerde(Serdes.Double())
    );
Attention aux late events — Par défaut, Kafka Streams rejette les messages arrivés hors fenêtre. Utilise TimeWindows.of(...).grace(Duration.ofSeconds(30)) pour tolérer les messages en retard.
